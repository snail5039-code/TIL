## 1. PDF 문서의 구성 요소 추출

### 1-1. PDF 본문과 좌표

PDF는 글자, 선, 도형, 이미지를 페이지의 특정 좌표에 배치한 문서이다. `pdfplumber`는 각 요소의 좌표를 읽어 표와 이미지가 있는 위치를 찾을 수 있다.

영역 좌표인 경계 상자(Bounding Box)는 다음 순서로 구성된다.

```python
(x0, top, x1, bottom)
```

| 값 | 의미 |
|---|---|
| `x0` | 영역의 왼쪽 좌표 |
| `top` | 영역의 위쪽 좌표 |
| `x1` | 영역의 오른쪽 좌표 |
| `bottom` | 영역의 아래쪽 좌표 |

### 1-2. 표 후보 선택과 추출

`page.find_tables()`로 페이지의 표 후보를 찾고 `table.bbox`로 좌표를 저장한다. 사용할 페이지와 표 번호를 지정한 뒤, 해당 영역만 잘라 원본 표를 확인한다.

```python
tables = page.find_tables()
table_bbox = selected_table["bbox"]
region = page.crop(table_bbox)
```

표는 가로선과 세로선의 교차점을 기준으로 셀을 구성한다. 바깥쪽 세로선이 빠진 표는 표 영역의 좌우 좌표를 가상 경계선으로 추가한다.

```python
table_settings = {
    "vertical_strategy": "lines",
    "horizontal_strategy": "lines",
    "explicit_vertical_lines": [table_bbox[0], table_bbox[2]],
}
corrected_rows = region.find_tables(table_settings)[0].extract()
```

표 아래에서 `*`로 시작하는 줄은 각주로 분리한다. 각주는 표의 수치나 조건을 보충하는 설명이므로 표와 함께 보관한다.

### 1-3. 병합 셀과 Markdown 표

병합된 첫 번째 열이 빈칸으로 추출되면 직전에 확인한 분류 값을 저장했다가 채운다.

```python
if row[0]:
    current_category = row[0]
else:
    row[0] = current_category
```

이 방식은 첫 번째 열의 빈칸이 병합 셀이라는 전제에 따라 동작한다. 정리한 헤더와 행은 Markdown 표 문자열로 조합하고, 페이지 번호·영역 좌표·표 ID·행과 열 구조를 함께 저장한다.

### 1-4. 이미지 추출과 Gemini 해석

`page.images`로 PDF 내부 이미지 객체를 찾고, 이미지 면적을 페이지 전체 면적으로 나누어 후보를 고른다. 실습에서는 페이지 면적의 10%를 초과하는 이미지를 선택했다.

```python
area_ratio = image_area / page_area
selected_images = [
    image for image in image_candidates
    if image["area_ratio"] > 0.10
]
```

선택한 영역은 PNG로 렌더링한 뒤 `BytesIO` 메모리 버퍼에 저장한다. PNG 바이트를 Base64 문자열로 변환해 추출 지시문과 함께 Gemini에 전달하고, 결과를 Markdown 텍스트로 저장한다.

```plain text
이미지 영역 자르기
→ PNG로 렌더링
→ 메모리 버퍼에 저장
→ Base64 인코딩
→ Gemini가 이미지 내용 해석
→ Markdown 텍스트 저장
```

## 2. 본문·표·이미지 블록 재조립

표와 이미지 영역 안의 기존 글자를 그대로 두면 새로 만든 Markdown 표와 이미지 해석문이 중복된다. 따라서 글자 중심점이 해당 영역 안에 있으면 기존 글자를 제외하고, 정리된 표와 이미지 해석문을 다시 넣는다.

```plain text
표·이미지 영역의 기존 글자 제외
→ 남은 본문을 text 블록으로 생성
→ table·image 블록 추가
→ bbox 위치로 정렬
→ 연속된 본문 줄 병합
```

각 블록에는 미리 유형 이름표를 붙인다.

| `content_type` | 저장되는 내용 |
|---|---|
| `text` | PDF의 일반 본문 |
| `table` | 행·열과 각주를 보존한 Markdown 표 |
| `image` | Gemini가 이미지에서 추출한 Markdown 텍스트 |

페이지·파일명·추출 방식·블록 ID·표 ID·이미지 ID는 메타데이터로 유지한다. 블록별 글자 수 출력은 청킹 자체가 아니라 유형 분리 결과와 각 블록의 크기를 점검하기 위한 것이다.

## 3. 유형별 청킹

### 3-1. 일반 청킹

재귀적 문자 텍스트 분할기(Recursive Character Text Splitter)는 문단과 줄바꿈 등의 경계를 이용해 목표 글자 수에 맞춰 텍스트를 나눈다.

```python
splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=100,
)
```

`chunk_overlap`은 앞뒤 청크의 문맥이 완전히 끊어지지 않도록 일부 내용을 겹치는 목표값이다. 그러나 본문·표·이미지를 합친 문자열에 일반 청킹을 적용하면 표의 헤더와 데이터 행이 서로 다른 청크로 나뉠 수 있다.

### 3-2. 표 보호와 행 단위 분할

짧은 표는 통째로 유지할 수 있지만, 큰 표를 하나의 청크로 보관하면 기준 길이를 크게 초과한다. 이를 해결하기 위해 표는 **행과 행 사이에서만** 나누고 각 청크에 헤더와 각주를 반복한다.

```plain text
헤더 + 데이터 1~3행 + 각주
헤더 + 데이터 4~6행 + 각주
헤더 + 나머지 행 + 각주
```

다음 행을 넣었을 때 기준 길이를 넘으면 현재까지 모은 행을 먼저 저장한다. 새로운 청크의 첫 행은 한 행만으로 기준을 초과해도 중간에서 자르지 않는다.

```python
if current_rows and len(candidate) > chunk_size:
    parts.append(render_table(current_rows))
    current_rows = []

current_rows.append(row)
```

### 3-3. 유형에 따른 처리

`split_document_blocks()`는 `content_type`을 보고 청킹 방식을 선택한다.

```plain text
text  → 일반 글자 수 청킹
image → Gemini가 추출한 텍스트를 일반 청킹
table → 행 단위 청킹 + 헤더·각주 반복
```

실습의 300자는 표가 잘리는 현상을 확인하기 위한 비교값이다. 설계에서는 `300/50`과 `800/100`을 비교하고, 설정별 벡터DB를 따로 저장한다.

## 4. 일반 청킹과 Semantic Chunking

일반 청킹은 정해진 글자 수와 구분자를 기준으로 먼저 자른 뒤, 완성된 청크를 임베딩한다.

```plain text
문서 분할
→ 청크 임베딩
→ 벡터DB 저장
```

의미 기반 청킹(Semantic Chunking)은 문장마다 임베딩한 뒤 인접 문장의 유사도를 비교한다. 유사도가 크게 떨어지는 지점을 주제 전환으로 보고 청크를 구성한 다음, 완성된 청크를 검색용으로 다시 임베딩한다.

```plain text
문장 단위 분리
→ 각 문장 임베딩
→ 인접 문장 유사도 비교
→ 의미가 바뀌는 지점에서 청크 구성
→ 완성된 청크 다시 임베딩
→ 벡터DB 저장
```

| 구분 | 일반 청킹 | Semantic Chunking |
|---|---|---|
| 분할 기준 | 글자 수·문단·줄바꿈 | 문장 사이의 의미 유사도 |
| 임베딩 | 완성된 청크에 수행 | 경계 탐색과 검색 저장에 수행 |
| 특징 | 빠르고 결과를 설명하기 쉬움 | 의미 경계를 반영하지만 비용과 시간이 증가 |

이번 실습은 약 1,258페이지의 공문서가 대상이며 제목, 문단, `□`, `○` 같은 구조 기호가 존재한다. 따라서 Semantic Chunking은 제외하고 구조 기반 구분자를 사용하는 일반 청킹으로 비교한다.

## 5. RAG Agent 설계

### 5-1. 문서 처리 파이프라인

59개 PDF에서 금융·공공·커머스·법률·의료 문서를 처리한다. 추출은 한 번만 실행하고 페이지별 결과를 JSONL로 저장한 뒤, 청킹 실험에서는 저장된 결과를 다시 불러온다.

```plain text
PDF
→ 텍스트·표·이미지 추출
→ 페이지별 JSONL 저장
→ JSONL에서 블록 로드
→ 설정별 청킹
→ 임베딩
→ 설정별 벡터DB 저장
```

자동 처리에서는 1행 표나 안내 박스처럼 잘못 감지된 표를 걸러야 한다. 선으로 그린 벡터 차트는 이미지 객체로 잡히지 않을 수 있으므로 실패 사례로 기록한다. 평가용 `golden_set.csv`는 검색 DB에 넣지 않고 PDF만 색인한다.

### 5-2. 단일 Agent와 재검색 흐름

현재 기능은 문서 검색 하나이므로 분야별 Agent와 Supervisor로 나누지 않고 단일 Agent를 사용한다. 분야는 `domain` 메타데이터로 관리하고 검색 기능은 도구로 제공한다.

```plain text
질문 입력
→ 검색 도구로 상위 k개 청크 검색
→ LLM이 근거 충분성 판단
→ 충분하면 파일명·페이지와 함께 답변
→ 부족하면 검색어를 바꿔 재검색
→ 최초 검색 포함 최대 3회
→ 계속 부족하면 답변 보류
→ 질문·답변·청크 ID·근거·시간 저장
```

재검색과 종료 흐름은 LangGraph 노드로 구성한다. 계산이나 웹 검색처럼 도구 종류가 늘어날 경우 Supervisor 구조를 추가 실험 대상으로 남긴다.

### 5-3. 검색기 비교 순서

기본 검색은 Chroma와 Google 임베딩을 이용한 Similarity Search로 시작한다. 청킹 설정을 결정할 때는 검색 방식을 고정하고, 이후 청킹을 고정한 상태에서 검색기를 비교한다.

```plain text
Similarity로 청킹 비교
→ 선택한 청킹 설정 고정
→ Similarity·BM25·Hybrid 비교
→ 선택한 검색기로 기본 RAG 구성
→ 재검색 Agent와 비교
```

개념 질문은 Similarity Search, 숫자·사건번호·고유명사 질문은 BM25의 검색 결과를 확인한다. Hybrid Search는 두 결과를 RRF(Reciprocal Rank Fusion)로 결합하고, Re-ranking과 domain 필터는 이후 개선 항목으로 둔다.

## 6. Golden Set과 평가

Golden Set은 질문, 기준 답변, 원문 근거, 파일명과 페이지를 연결한 RAG 평가 기준이다. 먼저 직접 작성한 소규모 문항으로 빠르게 확인한 뒤 제공된 268개 문항으로 비교한다.

| 항목 | 내용 |
|---|---|
| 질문 | RAG에 입력할 사용자 질문 |
| 기준 답변 | 답변에 포함되어야 하는 핵심 내용 |
| 근거 구절 | 기준 답변을 뒷받침하는 원문 |
| 파일명·페이지 | 근거를 다시 찾을 수 있는 위치 |
| `domain` | 금융·공공·커머스·법률·의료 구분 |
| `context_type` | 문단·표·이미지 구분 |
| 답변 가능 여부 | 문서로 답할 수 있는지 여부 |

직접 작성하는 Golden Set은 분야별 4~6개씩 총 20~30개로 구성하고, 문단·표·이미지 질문을 섞는다. 문서에 답이 없는 질문도 3~5개 포함해 Agent가 근거 없이 답하지 않고 보류하는지 확인한다.

평가 순서는 다음과 같다.

```plain text
직접 만든 Golden Set으로 빠른 확인
→ 제공된 268개 문항으로 확대 평가
→ 청킹 비교
→ 검색기 비교
→ 기본 RAG와 재검색 Agent 비교
```

검색은 `Hit@k`와 MRR, 답변은 LLM 채점, 답변 불가 문항은 보류 성공 여부로 평가한다. 응답 시간과 평균 검색 횟수도 함께 기록한다.

## 7. 헷갈린 점

처음에는 유형별 청킹에서 본문과 이미지는 300자, 표는 700자처럼 서로 다른 길이를 사용하는 것으로 이해했다. 실제 코드는 모든 유형에 같은 `chunk_size`를 전달하지만, 본문과 이미지 해석문은 일반 청킹하고 표는 행 중간을 자르지 않는다는 차이가 있었다.

또한 이미지 블록을 청킹한다는 것은 원본 이미지를 자른다는 뜻이 아니었다. 먼저 Gemini가 이미지를 Markdown 텍스트로 변환하고, 청킹 단계에서는 그 텍스트를 일반 본문처럼 나누는 과정이었다.
