    def __init__(self, name, price, stock):
        self.name = name
        self.price = price
        self.stock = stock

    def __str__(self):
        return self.name

    def __repr__(self):

from abc import ABC, abstractmethod

class Payment:

    @abstractmethod
    def pay(self, price: int):

        pass

class CashPayment:

    def __init__(self, cash: int):
        # 현금을 가집니다.
        self.cash = cash

    def pay(self, price: int) -> bool:

        if self.cash >= price:
            self.cash -= price
            return True

        return False

class CardPayment:

    def __init__(self, card_limit, card_usage):
        self.card_limit = card_limit
        self.card_usage = card_usage

        
    def pay(self, price: int) -> bool:
        '''성공하면 True, 실패하면 False를 반환하는 함수'''
        if self.card_usage + price <= self.card_limit:
            self.card_usage += price
            return True

        return False

### `*args`, `**kwargs`

- `*args`: 여러 개의 위치 인자를 튜플로 받는다.
- `**kwargs`: 여러 개의 키워드 인자를 딕셔너리로 받는다.

함수를 정의할 때는 여러 인자를 하나로 모으고, 함수를 호출할 때는 `*`, `**`로 묶인 값을 펼친다.
```

```python
def show_info(*args, **kwargs):
    print(args)
    print(kwargs)

show_info(10, 20, name="철수", age=25)
```

```markdown
### 패킹과 언패킹

패킹은 여러 값을 하나로 묶는 것이고, 언패킹은 묶인 값을 다시 펼치는 것이다. 함수 호출에서 `*`는 리스트나 튜플을, `**`는 딕셔너리를 펼친다.
```

```python
numbers = (10, 20, 30)  # 패킹
a, b, c = numbers       # 언패킹
print(a, b, c)

def add(x, y):
    return x + y

values = [10, 20]
print(add(*values))

def introduce(name, age):
    print(name, age)

user = {"name": "영희", "age": 20}
introduce(**user)
```

```markdown
### 리스트의 얕은 복사와 깊은 복사

`b = a`는 복사가 아니라 두 변수가 같은 리스트를 가리키는 대입이다.

- 얕은 복사: 바깥 리스트만 새로 만들고 내부 리스트는 공유한다.
- 깊은 복사: 내부 리스트까지 모두 새로 만든다.
```

```python
import copy

original = [[1, 2], [3, 4]]
shallow = original.copy()
deep = copy.deepcopy(original)

original[0].append(100)

print("원본:", original)
print("얕은 복사:", shallow)
print("깊은 복사:", deep)
```

```markdown
### `__str__`과 `__repr__`

- `__str__`: 사용자가 보기 편한 문자열이다. 객체를 `print()`하면 주로 이 메서드가 사용된다.
- `__repr__`: 개발자가 객체의 정보를 확인하기 위한 문자열이다.
```

```python
class Product:
    def __init__(self, name, price):
        self.name = name
        self.price = price

    def __str__(self):
        return f"{self.name} - {self.price}원"

    def __repr__(self):
        return f"Product({self.name!r}, {self.price})"

product = Product("키보드", 50000)
print(str(product))
print(repr(product))
```

```markdown
### `is`와 `==`

- `==`: 두 객체의 값이 같은지 비교한다.
- `is`: 두 변수가 같은 객체를 가리키는지 비교한다.

숫자나 문자열 같은 값 비교에는 `is`를 사용하지 않고 `==`를 사용한다. `None` 비교에는 `is None`을 사용한다.
```

```python
a = [1, 2, 3]
b = [1, 2, 3]
c = a

print(a == b)  # True: 값이 같다.
print(a is b)  # False: 서로 다른 객체이다.
print(a is c)  # True: 같은 객체이다.

value = None
print(value is None)
```

```markdown
### 제네릭

```markdown
### 덕 타이핑과 `Protocol`

덕 타이핑은 클래스의 종류보다 필요한 기능이 있는지를 보는 방식이다. `Protocol`은 필요한 메서드를 타입 힌트로 나타낸다.

#### ABC 대신 덕 타이핑을 사용하는 이유

ABC(Abstract Base Class)는 공통 부모 클래스를 상속하게 하여 구현 규칙을 강제한다. 반면 덕 타이핑은 상속 관계가 없어도 필요한 메서드만 가지고 있으면 사용할 수 있다.

- 클래스 사이의 결합도가 낮아진다.
- 기존 클래스나 외부 라이브러리의 클래스를 수정하지 않고 사용할 수 있다.
- 서로 관련 없는 클래스도 같은 기능을 제공하면 동일하게 처리할 수 있다.
- `Protocol`을 함께 사용하면 덕 타이핑의 유연성을 유지하면서 정적 타입 검사도 받을 수 있다.

공통 구현을 재사용하거나 실행 중에 상속 규칙을 강제해야 한다면 ABC가 적합하고, 상속 관계보다 객체가 제공하는 기능이 중요하다면 덕 타이핑이 적합하다.
```

```python
from typing import Protocol

class Speaker(Protocol):
    def speak(self) -> str:
        pass

class Dog:
    def speak(self) -> str:
        return "멍멍"

class Cat:
    def speak(self) -> str:
        return "야옹"

def make_sound(animal: Speaker):
    print(animal.speak())

make_sound(Dog())
make_sound(Cat())

```

```markdown
### 제너레이터

제너레이터는 모든 결과를 한꺼번에 메모리에 올리지 않고, **필요할 때마다 값을 하나씩 생성**하여 반환하는 도구이다.

- 일반 함수(`return`): 계산이 끝나면 결과를 반환하고 종료한다.
- 제너레이터(`yield`): 값을 하나씩 반환하고 실행을 일시 정지한다.

#### 리스트를 만들어 순회하는 대신 제너레이터를 사용하는 이유

일반적인 `for` 문은 리스트와 같은 반복 가능한 객체에서 값을 꺼내 사용한다. 제너레이터는 `for` 문을 대체하는 것이 아니라, `for` 문에 값을 하나씩 제공하는 반복 가능한 객체를 만드는 방식이다.

- 모든 값을 미리 저장하지 않아 메모리를 적게 사용한다.
- 첫 번째 값을 만든 즉시 처리를 시작할 수 있어 대기 시간이 줄어든다.
- 파일 읽기, 스트리밍 데이터, 무한 수열처럼 전체 크기를 알 수 없는 데이터도 처리할 수 있다.
- 필요한 시점에만 값을 계산하므로 사용하지 않는 값에 대한 연산을 줄일 수 있다.

데이터가 작고 여러 번 반복해서 사용해야 한다면 리스트가 편리하다. 데이터가 크거나 한 번만 순서대로 처리한다면 제너레이터가 적합하다.
```

```python
def simple_generator():
    print("첫 번째 값을 생성합니다.")
    yield "A"

    print("두 번째 값을 생성합니다.")
    yield "B"

    print("세 번째 값을 생성합니다.")
    yield "C"

gen = simple_generator()

# next()를 호출할 때마다 다음 yield까지 실행된다.
print(f"받은 값: {next(gen)}")
print(f"받은 값: {next(gen)}")
print(f"받은 값: {next(gen)}")

```

```python
gen = simple_generator()

# for 문은 내부적으로 next()를 호출한다.
for text in gen:
    print(text)

    try:
        result = client.interactions.create(
            model=model, input=prompt, store=False,
        )
        return result.output_text
    except errors.ClientError as error:

```markdown
## Pydantic으로 원하는 응답 구조 정의하기

### Pydantic이란?

Pydantic은 Python의 타입 힌트를 이용해 데이터의 구조를 정의하고 검증하는 라이브러리입니다. 일반 class처럼 모델을 만들지만, 전달받은 값이 선언한 자료형과 조건에 맞는지도 검사합니다.

이번에는 Gemini가 다음 구조로만 답하도록 요청합니다.

```json
{
  "sentiment": "positive | neutral | negative",
  "summary": "한 문장 요약",
  "keywords": ["핵심어"]
}
```

사람에게는 위의 JSON 예시만으로 구조를 설명할 수 있지만, Gemini와 프로그램에는 더 명확한 규칙이 필요합니다. 이 규칙을 표준 형식으로 표현한 것이 **JSON Schema**입니다. JSON Schema에는 필드 이름, 자료형, 필수 여부와 허용값 등이 들어갑니다.

JSON Schema를 dictionary로 직접 작성할 수도 있지만, 필드가 많아지면 모델 코드와 schema를 따로 관리해야 합니다. 여기서는 Pydantic 모델을 먼저 정의하고, 그 모델로부터 JSON Schema를 자동 생성합니다. 그러면 같은 모델을 Gemini 응답 형식 지정과 실제 응답 검증에 함께 사용할 수 있습니다.
```

```python
class ReviewAnalysis(BaseModel):
    model_config = ConfigDict(extra="forbid")

    sentiment: Literal["positive", "neutral", "negative"]
    summary: str = Field(max_length=30)
    keywords: list[str] = Field(min_length=2, max_length=2)

# Pydantic 모델을 Gemini에 전달할 JSON Schema로 변환합니다.
review_schema = ReviewAnalysis.model_json_schema()
pprint(review_schema)
```

```markdown
### Pydantic 모델 코드 읽기

- `BaseModel`: 데이터 모델을 만들기 위해 상속하는 Pydantic의 기본 class입니다.
- `Literal`: `sentiment`를 세 문자열 중 하나로 제한합니다.
- `Field`: 문자열 길이나 list 원소 개수 같은 추가 조건을 설정합니다.
- `ConfigDict(extra="forbid")`: 모델에 선언하지 않은 필드가 들어오면 검증에 실패하게 합니다.
- `model_json_schema()`: 모델의 타입과 조건을 JSON Schema dictionary로 변환합니다.

### 생성된 JSON Schema 읽기

- `type`: 값의 자료형입니다.
- `properties`: object 안에 들어갈 필드를 정의합니다.
- `enum`: 사용할 수 있는 값을 제한합니다.
- `items`: array 안에 들어갈 값의 자료형입니다.
- `required`: 반드시 있어야 하는 필드입니다.
- `additionalProperties: False`: 정의하지 않은 필드를 추가하지 못하게 합니다.
```

```markdown
### 모델과 맞지 않는 JSON 검증하기

JSON 문법이 올바르더라도 값이 Pydantic 모델의 조건과 맞지 않으면 `ValidationError`가 발생합니다. Gemini에 요청을 보내기 전에 잘못된 JSON을 직접 넣어 검증 실패 상황을 확인해 봅니다.
```

```markdown
## Structured Output 요청 보내기

### MIME type이란?

MIME type은 주고받는 데이터가 어떤 형식인지 나타내는 표준 문자열입니다. 예를 들어 일반 텍스트는 `text/plain`, HTML은 `text/html`, JSON은 `application/json`으로 표현합니다.

여기서 `mime_type="application/json"`은 Gemini에게 응답을 일반 문장이 아닌 **JSON 문법에 맞는 텍스트**로 만들라고 알려줍니다. 다만 MIME type은 JSON 내부에 어떤 필드가 있어야 하는지까지 정의하지 않습니다. 세부 구조와 제약 조건은 `schema`가 담당합니다.

`response_format`의 각 항목은 다음 역할을 합니다.

- `type: "text"`: 응답을 텍스트 출력으로 받습니다.
- `mime_type: "application/json"`: 그 텍스트의 형식을 JSON으로 제한합니다.
- `schema: review_schema`: JSON에 들어갈 필드, 자료형과 허용값을 제한합니다.

MIME type을 JSON으로 지정해도 Python이 곧바로 dictionary를 받는 것은 아닙니다. `output_text`에는 JSON 형식의 문자열이 들어오므로 이후에 `json.loads()`나 Pydantic으로 파싱해야 합니다.
```

```python
structured = client.interactions.create(
    model=model,
    input=(
        "다음 후기를 분석하세요. summary는 30자 이내, "
        f"keywords는 2개만 작성하세요.\n\n[후기]\n{review}"
    ),
    response_format={
        "type": "text",
        "mime_type": "application/json",
        "schema": review_schema,
    },
    store=False,
)

print(structured.output_text)
```
